You empty `staging/`, the vault's capture queue. Each capture becomes a note under
`public/posts/` — or is discarded. Nothing is published by this skill: you prepare notes
so that steps 2 to 4 can publish them.

This is the most frequent task in the whole workflow and the only one that used to be
entirely manual. It is also the one where haste costs most: a capture wrongly tagged is
invisible, and a capture published without a description is a thumbnail with nothing to
say.

## 0. Context — this skill runs from pixelle, not from the vault

The current directory is the **pixelle** repository; the content lives in a **different**
directory, the Obsidian vault.

- **Resolve the vault path** (same convention as `scripts/sync-vault.mjs`):
  ```bash
  VAULT="${VAULT_PATH:-/home/ipro0800/Documents/data/obsidian/petersVault}"
  ```
  Every path below is relative to the vault: prefix it with `$VAULT/`.
- **Never write to `content/`.** It is generated by `npm run sync`; a direct write there is
  overwritten or deleted. Mind the name clash: the `public/` of the **vault** is the
  publishable root, while the `public/` of the **pixelle repository** is Quartz's build
  output. They are unrelated.
- The three vault roots are `public/` (publishable), `private/` (never published, whatever
  the flag) and `staging/` (this queue).
- Any git command aimed at the vault is written `git -C "$VAULT" …`.
- Obsidian may be open: write normally, but never touch `$VAULT/.obsidian/`.

## 1. Read the queue before proposing anything

```bash
find "$VAULT/staging" -name '*.md' | sort
```

An empty queue is a normal outcome: say so in one line and stop. Do not go looking for
work elsewhere.

A capture is usually one markdown link and nothing else, sometimes with `created` /
`modified` and no other frontmatter:

```markdown
---
created: 2026-05-18
modified: 2026-05-18
---

[Edwy Mdp sur Instagram](https://www.instagram.com/reel/DXXnAzwgkxW/?igsh=MWoyYmJmdjFtMm56Zg==)
```

The filename is whatever the source page was called, which is often unusable as a title:
`✋🏻ABSOLUTE CINEMA🤚🏻 sur Instagram.md`.

## 2. Learn the conventions from what is already there — do not invent them

Before proposing anything, read the target folder. The taxonomy is **closed in practice**:
reuse an existing tag rather than coining one.

```bash
grep -rh 'post/' "$VAULT/public/posts" --include='*.md' \
  | grep -o 'post/[a-zé-]*' | sort | uniq -c | sort -rn
```

At the time of writing: `post/music` (29), `post/fitness` (14), `post/beauty` (10),
`post/social` (7), `post/dance` (7), `post/humor` (6), `post/poetry` (4), `post/movie` (4),
`post/series` (3), `post/history`, `post/science`, `post/unknown` (1 each). Run the command
anyway — the counts age, and a new theme may have been introduced deliberately since.

`post/unknown` exists for the capture you genuinely cannot place. Use it rather than
stretching another tag, and say so in your report.

Target shape of a triaged note:

```markdown
---
tags:
  - post/music
publish: true
description: Barenboim explique en trois minutes pourquoi l'Appassionata ne se joue pas vite.
created: 2026-05-18
modified: 2026-05-18
---

[Barenboim sur l'Appassionata](https://www.youtube.com/watch?v=…)
```

- `publish: true` — without it the note stays invisible. This is what makes the capture a
  post.
- `tags` — exactly one `post/<theme>` in nearly every case.
- `description` — one sentence, in French, saying **why this is worth keeping**. Not a
  summary of the page title. This is the line that turns a bookmark into a recommendation,
  and it is the only part a reader sees before clicking.
- `created` / `modified` — keep the capture's own dates. If absent, use the file's date
  rather than today's: the queue is often weeks behind.

Leave the body as the bare markdown link. **Do not** turn it into a thumbnail or an
`<iframe>` by hand: `scripts/sync-vault.mjs` does that at sync time, downloading the
thumbnail and building a facade that contacts no third party before the click. A note that
already contains HTML defeats it.

## 3. Propose, then wait

Never write before the user has seen the list. For each capture, propose in one table row:

| capture | title | tag | description | destination |

- **title** — the note's future filename. Strip the noise (`… sur Instagram`, emoji, ALL
  CAPS) and name the *content*, not the page: `Barenboim sur l'Appassionata`, not
  `✋🏻ABSOLUTE CINEMA🤚🏻 sur Instagram`. French, no trailing punctuation.
- **destination** — `public/posts/` in almost every case. A capture that deserves a written
  billet goes to `public/blog/` instead, and you say so rather than deciding alone. A
  capture about health, work or the house belongs in `private/` — propose that, never
  publish it.
- Propose **discarding** the captures that no longer deserve anything (a dead link, a
  duplicate of an existing post). Deleting is a legitimate outcome of triage.

Open the link when the title alone does not let you write an honest description
(`WebFetch`). Do not invent what a video contains. If the page cannot be read, say so and
propose `post/unknown` with a description drawn from the title only — flagged as such.

Then ask **once**, for the whole batch. One grouped question, recommended option first —
never one question per capture.

## 4. Write, after validation

For each accepted capture:

1. Check for a homonym before creating the file — two notes with the same name make short
   wikilinks ambiguous:
   ```bash
   find "$VAULT" -name "<Title>.md"
   ```
2. Write the note to its destination with the frontmatter of §2.
3. Remove the capture from `staging/` (`git -C "$VAULT" rm` if tracked, else `rm`). The
   queue must end empty, or the same capture is triaged twice next month.
4. If the capture brought an image, move it under `public/_assets/images/` and reference it
   with a **text alternative** — the audit refuses an embed without one:
   ```markdown
   ![[2026-05-18-name.png|Ce que montre l'image]]
   ```

## 5. Commit the vault

One commit for the batch, in French, subject in the imperative:

```bash
git -C "$VAULT" add -- public/posts staging
git -C "$VAULT" commit -m "Trie N captures depuis staging"
```

Stage **only** the paths you touched. The vault often carries unrelated work in progress
under `private/`; sweeping it into your commit is a real risk, and `git -C "$VAULT" add -A`
is therefore forbidden here.

The vault is a git repository also synchronised by Obsidian Sync: plain commits only, never
a rebase, never a force push.

## 6. Hand over

Triage does not publish. Close by telling the user what comes next, and stop there:

> N captures triées, la file est vide. Pour publier : `/2-site-construct-locally`, puis
> `/3-site-check-local`, puis `/4-site-commit-and-publish`.

## Output contract

Be brief. The user wants to decide, not to read.

1. **One line of scope**: `N captures in the queue`.
2. **One table**, one capture per row (§3). No prose between rows.
3. **One grouped question**.
4. After writing: one line per outcome — created, discarded, moved to `private/`.

Do not print the commands you ran or the file contents you wrote.

## Verified pitfalls

- **The queue is the source of truth, not your memory.** Re-run the `find` after writing:
  anything left is something you forgot.
- **A capture is not a billet.** `posts/` is a collection of links; `blog/` is written
  prose. Sending a capture to `blog/` because it seems important produces an empty billet —
  the audit reports it as a note with no body.
- **Do not add a key that no other post carries.** `note-properties` runs with
  `includeAll: true`: any new frontmatter key becomes a visible row on the published page,
  and the audit flags it as an exposure. `title`, `source` and `author` exist on two or
  three posts only — that is not a precedent, it is drift.
- **Instagram and YouTube links keep their query string.** Do not clean up `?igsh=…` by
  hand; the sync extracts the identifier itself, and a truncated URL may stop resolving.
